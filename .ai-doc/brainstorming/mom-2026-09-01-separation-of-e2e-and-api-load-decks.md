## 1. Latar Belakang & Masalah

Sebelumnya, terdapat asumsi bahwa skenario kustom bisa dijalankan secara "hybrid" (mencampurkan langkah interaksi browser DOM dengan pengetesan beban HTTP dalam satu alur skenario yang sama).

**Koreksi Arsitektur dari User:**
Pengujian kustom **tidak boleh dicampur (non-hybrid)** karena memiliki karakteristik, tujuan, dan profil resource yang bertolak belakang:
1. **Playwright E2E Browser Testing:** Berfokus pada pengujian fungsional dan visual (buka browser, isi form input, klik menu/tombol, assert teks), serta membutuhkan **Interactive Live Viewport Frame** untuk memantau proses interaksi DOM secara visual dan mengumpulkan screenshot bukti.
2. **REST API Load Testing (Artillery Engine):** Berfokus pada otomatisasi REST API, *API Chaining* (misal: POST Login ➔ Ekstrak Token ➔ GET Protected Endpoint), dan penembakan beban masif dengan Virtual Users (1–100 VUs) untuk mengukur throughput (RPS), latensi persentil (p50..p99), serta error rate.

Oleh karena itu, dashboard dan engine harus **dipisahkan secara tegas menjadi 2 halaman / deck mandiri**.

## 2. Masukan & Perspektif Persona

### Melon 🏗️ (Technical Architect):
> *"Secara arsitektur (Bounded Context), Playwright adalah **DOM-Level Client Simulator** yang berat prosesnya, sedangkan Artillery/HttpLoadWorker adalah **Protocol-Level Traffic Generator** yang ultra-ringan. Memisahkannya menjadi 2 Deck mandiri di UI dan 2 Runner terisolasi di backend membuat kode jauh lebih maintainable, zero-coupling, dan mencegah kebingungan pengguna."*

### Sultan ⚙️ (Senior Backend Engineer):
> *"Dari sisi reliabilitas VPS, menjalankan 50–100 instance Chromium Playwright secara serentak akan langsung memicu Out-Of-Memory (OOM) crash. Sebaliknya, 100 Virtual Users pada REST API load test hanya memakan ~25MB RAM. Pemisahan deck ini menjamin safety guardrail VPS kita tetap kokoh."*

### Bernadya ✨ (Creative Visionary / UI):
> *"Dari sisi visual di Dashboard Risograph, kita buatkan **Two-Deck Tab Bar** di bagian atas:*
> * *Tab 1: 🎭 **PLAYWRIGHT E2E STUDIO** — Dilengkapi Step Builder (GOTO, FILL, CLICK, WAIT, ASSERT), Live View Frame / Process Visualizer, dan Screenshot Timeline.*
> * *Tab 2: ⚡ **REST API LOAD DECK** — Dilengkapi API Chaining Builder (Request Steps, Variable Extraction `{{token}}`), Slider VUs (1–100), Load Profile, dan Live Telemetry Chart 3-Series."*

### Nindi 🔬 (QA & Diagnostician):
> *"Pemisahan ini membuat assertion jauh lebih jelas:*
> * *Di E2E Studio: Assertions berfokus pada DOM selector, visibility, dan text match di layar browser.*
> * *Di API Load Deck: Assertions berfokus pada HTTP status code (200, 201), JSON Path response, dan SLA p95 latency threshold."*

### Lugi 📊 (Data Specialist):
> *"Database SQLite kita (`test_runs`, `test_executions`, `metric_points`) sudah sangat siap mendukung pemisahan ini:*
> * *Eksekusi E2E mencatat record di `test_executions` lengkap dengan `screenshot_path`.*
> * *Eksekusi API Load mencatat time-series di `metric_points` (RPS, p50..p99) dan ringkasan 12 metrik di `test_runs`."*
